## 1. Things only you can do (credential-gated)

Nothing here is blocked on code. All of it is written, deployed, and waiting on an
account or token.

### (a) Offsite backup — the one real risk ⛔ HIGHEST PRIORITY

**Today, every backup lives on the same disk as the database it backs up.**
3.1 GB of dumps, WAL, and basebackups on `/dev/sda1`. If the Hetzner box is lost,
all of it goes with it. Backups are excellent *against corruption and bad deploys*,
and worth nothing *against losing the box*.

The nightly `offsite-backup` cron runs and logs, every night:

```
[offsite-backup] OFFSITE_RCLONE_REMOTE not set — no offsite copy is being made
```

**Fix (~20 min):** create a Cloudflare R2 bucket (free tier is enough — the payload
is ~250 MB/night) and an S3 API token, then on the VPS:

```bash
ssh -i ~/.ssh/recrutas_cron root@178.156.193.183
cd /opt/recrutas/app && bash infra/vps/setup-offsite.sh
```

The script prompts for credentials with **no echo**, writes them straight into
`rclone.conf` / `.env`, generates the GPG passphrase, makes you acknowledge saving
it, tests bucket access, and runs the first push. Nothing secret becomes an
argument, a log line, or a transcript entry.

> **Save the GPG passphrase somewhere off this machine.** Encrypted backups you
> cannot decrypt are not backups. This is the single point where the whole chain
> can silently become worthless.

### (b) Hetzner snapshot backups
`hcloud` v1.67 is already installed at `~/.local/bin/hcloud`. Needs a Hetzner API token:

Box-level recovery, complementary to (a). ~20% of server cost.

## 2. What will reach you while you're away

**Alert delivery is verified end-to-end, not assumed.** A real test alert was sent
through the live path and confirmed delivered to `abaskabato@gmail.com` at
2026-07-26 04:56:48 UTC.

| Channel | Covers | Runs on |
|---|---|---|
| Cron failure email (Resend → `ADMIN_EMAILS`) | any of the 18 cron jobs failing, timing out, or OOM-killed | the VPS |
| `healthcheck-db.sh`, every 15 min | Postgres down, WAL archiver failing, `pg_wal` > 4 GB | the VPS |
| **GitHub Actions watchdog, hourly** | **the whole box being dead** | **off-box** |

The third one matters most. Every other alert runs *on* the VPS, and a dead box
sends nothing — silence would otherwise read as healthy. The watchdog hits
`/api/platform/stats` (app → VPS Postgres) and `/api/health/pipelines` (cron
freshness, 26 h), and GitHub emails you on failure.

Confirmed today: the hourly `schedule:` trigger fired on its own at 04:44 UTC and
passed — the dead-man's switch is genuinely armed, not merely committed.

> ⚠️ **Two caveats.** GitHub disables scheduled workflows after **60 days of repo
> inactivity** — if you're away longer than that, the watchdog dies silently. A
> single commit resets the clock. GitHub also delays scheduled runs under load, so
> treat it as a good free backstop, not a hard SLA.

**If you get a cron-failure email:** it's rate-limited per job, so you won't be
buried. Most jobs are idempotent and recover on the next scheduled run — a single
failure is usually not worth acting on. Sustained failure of `vps-db-health`, or
any watchdog failure, is worth acting on.

## 5. If something breaks while you're away

```bash
ssh -i ~/.ssh/recrutas_cron root@178.156.193.183

tail -50 /opt/recrutas/logs/<job>.log      # per-job logs
systemctl status postgresql                 # DB up?
df -h /                                     # disk
cd /opt/recrutas/app && git log --oneline -1 # deployed SHA
```

- **Postgres down:** it has auto-restart configured; `systemctl restart postgresql`
  if it's genuinely stuck.
- **Disk filling unexpectedly:** almost certainly WAL — check
  `du -sh /opt/recrutas/backups/wal` and whether `basebackup` (Sunday 08:00 UTC)
  has been failing, since that's what prunes it.
- **Need to restore:** `infra/vps/verify-restore.sh` shows the exact working
  restore procedure. PITR runbook is in `infra/vps/README.md`.
- **Deploying:** `bash infra/vps/push-deploy.sh` from the dev machine. Do **not**
  `git pull` on the VPS — it holds no GitHub credentials by design.

**Rollback of last resort:** the DB can be pointed back at Supabase by flipping
`DATABASE_URL`; the Supabase project is intact.
